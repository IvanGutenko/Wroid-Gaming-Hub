# Модель мышиного прицела (mouse aim)

Стабильная версия: тег **`stable-aim-v3`** (коммит `c3a7ad1`), проверена вживую в
Standoff 2 — плавное медленное ведение и резкие развороты на 180°+ без мёртвых фаз.
Откат: `git checkout stable-aim-v3`.

Реализация: `crates/wroid-runtime/src/mouse_aim.rs`. Профиль: `~/.config/wroid/profiles-v2/standoff-2.json`.

## Общая схема

Курсор мыши не рисуется. Каждое движение мыши превращается в движение **одного
виртуального пальца** внутри прямоугольной зоны экрана (region). Игра читает это
как обычный свайп и вращает камеру.

```
мышь dx/dy → масштабирование (sensitivity) → накопитель субпикселей
          → перемещение контакта в пределах region
          → если упёрлись в край или кончился бюджет пути → реконтер
```

## Компоненты

### 1. Масштабирование чувствительности (`MouseAimSensitivity`)
Рациональный множитель `numerator/denominator` (например 23/20 = 1.15).

### 2. Субпиксельный накопитель (`ScaleAccumulator`)
Целочисленное деление при сенсе < 1.0 съедает мелкие дельты целиком. Накопитель
хранит остаток от деления и прибавляет его к следующему событию — медленное
ведение пропорционально и не теряется. Остаток сбрасывается при смене режима
ADS (`set_ads_active`), чтобы скачок чувствительности не «выстреливал» накопленное.

### 3. Зона и центр (`MouseAimRegion`, origin)
Прямоугольник экрана, внутри которого живёт палец прицела. Текущие значения:

| параметр | значение | смысл |
|---|---|---|
| `region` | x 0.40–0.77, y 0.10–0.90 | зона свайпа |
| origin | (1123, 540) | точка старта/реконтера, центр зоны |
| запас хода | ±355 px по горизонтали | упор в край происходит редко |

Зона выбрана так, чтобы не задевать HUD-кнопки (джойстик слева ~x 0.16,
огонь/прыжок/присед справа x ≥ 0.81).

### 4. Политика замены контакта (свапы)

Свап — это новый `ACTION_DOWN` для игры: жест look перезапускается, и свап,
пришедшийся на мах, ощущается как пауза (измерено: бюджет 329 px при махах
500–800 px давал свап в каждом резком развороте). Поэтому контакт меняется
только в двух случаях:

1. **Тишина ≥ 40 мс** (`RECENTER_STILLNESS`) при пройденном пути ≥ половины
   запаса (`soft = travel_budget × 500 / 1000`). Свап в неподвижность
   невидим, а следующий мах начинается на свежем контакте. Тихие *события*
   разгонного участка маха тишиной не считаются — иначе свап падал бы на
   старт разворота (отвергнутая версия).
2. **Полный упор в край** (край поглотил всю дельту) — иначе контакт
   прилипает и вращение умирает.

Путь сам по себе (`travel_budget = min(полуширина, полувысота) ×
recenter_threshold_milli / 1000`) реконтер больше не форсирует: он задаёт
только, начиная с какого запаса свап в тишине имеет смысл. Чем шире зона,
тем реже срабатывают оба случая.

### 5. Реконтер (замена контакта)
Игра перестаёт читать дельты, когда палец неподвижен слишком долго или жест
«слишком длинный». Поэтому контакт периодически пересаживается. Кадр реконтера:

```
[ Down B @origin , Move B @clamp(origin+d) , Up A @старая позиция ]
```

Один кадр содержит все три события:
- новый палец B встаёт в **origin** (единственная гарантированно чистая точка);
- тем же кадром сдвигается на остаток дельты `d` — игра мгновенно перепривязывает
  жест и не теряет вращение;
- старый палец A поднимается.

Посадка строго в origin: посадка «на место старого пальца» стекает два касания
в одну точку на один кадр, и игра читает это как сломанный жест (прерывания,
нечёткая сенса) — эта версия была отвергнута.

Contact ID чередуются пинг-понгом (`next_contact_id = old`), чтобы Android
видел разные касания, а не «телепорт» одного.

### 6. Упор в край (edge clamp) — критический фикс
Если после сдвига целевая позиция совпадает с текущей (край поглотил всю дельту),
реконтер запускается **всегда**. Ранняя версия возвращала `Ignored`, когда
«и из origin дельта тоже упёрлась бы» — из-за этого контакт прилипал к краю и
камера умирала до смены направления. Именно это было одной из причин пауз при
резких поворотах: длинный однонаправленный свайп = длинная серия отброшенных
дельт. Сегодняшняя политика (раздел 4) — единственный мах-случай, где свап
ещё возможен: длинный мах, доехавший до края зоны.

### 7. Отложенный реконтер (pending recenter, gap > 0)
При ненулевом `recenter_gap` замена двухфазная: старый палец поднимается сразу,
новый садится через gap; движение, пришедшее во время ожидания, накапливается в
`PendingRecenter.dx/dy` и применяется одним Move после посадки. Текущий профиль
использует gap = 0 (однофазный вариант выше).

### 8. Reaffirm (поддерживающий Move)
Каждые `reaffirm_interval` (250 мс) контроллер посылает Move в текущую позицию,
чтобы игра не считала жест завершённым при паузе в движении мыши.

## Конфигурация профиля (binding `action.kind == "mouse_aim"`)

```json
{
  "action": {
    "kind": "mouse_aim",
    "contact": {"x": 0.585, "y": 0.50},
    "region": {"x": 0.40, "y": 0.10, "w": 0.37, "h": 0.80},
    "sensitivity": 1.15,
    "ads_sensitivity": 0.75,
    "recenter_threshold_milli": 1000,
    "reaffirm_ms": 250,
    "alternate_contact_id": 9
  }
}
```

## Диагностика

- `WROID_AIM_TRACE=1 wroid hub` — трейс решений контроллера
  (move/relocate/recenter) в stderr.
- Логи сессии: `~/.local/state/wroid/game-session.log`
  (`[stall]`-строки = задержки клавиатурного цикла).
- После пересборки обязательно `pkill -x wroid && pkill -x wroidd` — демон живёт
  долго и держит старый бинарник.
- Сборка только `-p wroid-cli` НЕ обновляет `target/release/wroidd` (демон живёт
  в крейте wroid-daemon). Если менялась схема профиля (`wroid-core`) или демон —
  собирайте весь workspace: `cargo build --release --workspace`, затем
  `./target/release/wroid desktop install`. Иначе установленный старый демон
  отвергнет новый профиль с «unknown variant» на новом действии.
